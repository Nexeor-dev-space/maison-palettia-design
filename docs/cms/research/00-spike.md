## 5. Gotchas — every one, with symptom, cause, fix

**G1. `ERR_REQUIRE_ASYNC_MODULE` from the Payload CLI.**
`npx payload generate:types` dies: `require() cannot be used on an ESM graph with top-level await
... Requiring @payloadcms/richtext-lexical/dist/index.js`. Cause: `package.json` has no
`"type": "module"`, so tsx treats `payload.config.ts` as CJS and `require()`s the ESM lexical
package. Every Payload template ships `"type": "module"`. Fix: add it. Checked: the only `.js` file
in the repo is the generated `importMap.js` (ESM) — `next.config.ts`, `eslint.config.mjs`,
`postcss.config.mjs` are unaffected. Next itself is fine with it (build/dev/start all pass).

**G2. graphql must be 16.x.** `npm view graphql version` returns 17.0.2 but both `payload` and
`@payloadcms/next` peer on `^16.8.1`. Install `graphql@^16.8.1` explicitly (create-payload-app does
the same). `withPayload` also externalises `graphql` so only one copy loads at runtime.

**G3. `favicon.ico`, `robots.ts`, `manifest.*` are root-only; `sitemap`, `icon`, `apple-icon`,
`opengraph-image` are not.** Next's matcher (`next/dist/lib/metadata/is-metadata-route.js`) anchors
`^[\\/]robots…` and `^[\\/]manifest…` and `^[\\/]favicon\.ico$` to the `app/` root, but `sitemap`,
`icon`, `apple-icon`, `opengraph-image`, `twitter-image` match at any depth. Moving `robots.ts` into
`(site)` silently dropped `/robots.txt` from the build (404 verified); moving it back to
`app/robots.ts` restored it (200 verified). Metadata routes do not need a layout, so they are fine at
the layout-less root. If a `manifest.ts` is ever added, same rule.

**G4. Two root layouts, no `app/layout.tsx`.** `app/(site)/layout.tsx` keeps `<html>`/`<body>` and
all the site chrome; `app/(payload)/layout.tsx` is Payload's. Consequences: navigating between
`/admin` and the site is a full document load (correct); the two groups must never resolve the same
URL (G10); `/` lives in `(site)`.

**G5. Lenis / CursorLayer / PointerField / intro script / fonts / BottomNav do not reach `/admin`.**
They are all mounted in `(site)/layout.tsx`, so nothing to do. Verified: admin HTML contains no
`lenis`, no `montserrat_*` class, no `data-intro`. Do not move `<SmoothScroll>` upward.

**G6. Tailwind v4 + Payload SCSS coexist without config.** `globals.css` (`@import "tailwindcss"`,
`@theme static`, `@utility …`) is imported only by `(site)/layout.tsx`; `@payloadcms/next/css`
(292 KB) and `custom.scss` only by `(payload)/layout.tsx`. Turbopack compiled the `.scss` with the
`sass@1.77.4` that `@payloadcms/next` depends on — no `sass` install, no `sassOptions`. Tailwind's
automatic source scanning will read `app/(payload)/**` (harmless; nothing there uses utilities).
If the admin ever needs brand colours, put them in `custom.scss` using Payload's `--theme-*` vars.

**G7. `withPayload` adds a `webpack()` function, and Turbopack `next build` still passes.** The
Next 16 upgrade guide says a custom webpack config fails the build; in 16.3.4 the only effect of
`config.webpack` (`next/dist/build/index.js` ~L930) is `has-custom-webpack-config=true` and
disabling the webpack build worker, which Turbopack does not use. Keep `"build": "next build"`
(Turbopack). Do **not** add `--webpack`.

**G8. "Experiments (use with caution): ⨯ turbopackServerFastRefresh" banner** in dev and build output
is `withPayload` turning that experiment off for HMR. Expected; ignore.

**G9. No `middleware.ts`/`proxy.ts` in the repo.** If Phase 1 adds one (Next 16 name is `proxy.ts`,
Node runtime only), its `matcher` must exclude `/admin/:path*`, `/api/:path*`, `/_next/:path*`.

**G10. Reserved paths.** `/admin/*` and `/api/*` belong to Payload. A site route handler at
`app/(site)/api/<static-name>/route.ts` still wins over `api/[...slug]` (verified), so Mamo Pay
webhooks can live either there or as Payload `endpoints` (which also land under `/api/...`).
Never name a site route the same as a collection slug (`/api/users`, `/api/media`, …) and never put
a page under `(site)/admin`.

**G11. Dev pushes schema; prod does not — and the only database is production.**
`@payloadcms/db-postgres/dist/connect.js`: `if (NODE_ENV !== 'production' && PAYLOAD_MIGRATING !== 'true'
&& this.push !== false) pushDevSchema()`. With `DATABASE_URL` pointing at the shared Postgres, any
`next dev` on any laptop would run drizzle-kit **push** against production (it prompts on data loss,
but still). Set `push: false` and treat migrations as the single path (`migrate:create` ->
commit -> `payload migrate` on the server). Also verified the other half: a production server with no
migrations applied answers 500 `no such table` on the first write. Deploy order is therefore
`npm ci` -> `npx payload migrate` -> `next build` -> start (build needs the tables because pages call
the Local API during prerender, G19). Alternative for a single-instance host: `prodMigrations:
migrations` (import `./migrations`) runs pending migrations at boot; fine for one process, racy for
several.

**G12. Relative paths resolve against `process.cwd()`, and standalone's cwd is not the repo.**
Running `node .next/standalone/server.js` from inside `.next/standalone` made `file:./spike.db` a
new empty file there (that was the 500 above). Postgres has no such issue, but Payload's default
`upload.staticDir` is `<cwd>/<slug>` (`media/`) and `migrationDir` defaults to `<cwd>/migrations`.
Rule for the server: start from the repo root (`node .next/standalone/server.js` with cwd = repo
root; `server.js` finds its own files via `__dirname`), keep `media/` there, back it up, and
gitignore it. Set `upload.staticDir` explicitly to an absolute path derived from the repo root
if the process manager cannot guarantee cwd. (`@payloadcms/storage-s3` later if desired.)

**G13. `output: "standalone"` works.** `sharp`, `libsql`, `@libsql`, `pino`, `payload`,
`@payloadcms/*` are traced in; `payload-types.ts` is traced in too (harmless, because the config
references its path). Usual Next rule: copy `public/` and `.next/static` into the standalone dir
(or serve them from the reverse proxy). Also the CLI (`payload migrate`) is run from the source
checkout, not from the standalone bundle.

**G14. `/api/graphql-playground` is 404 in production** — `graphQL.disablePlaygroundInProduction`
defaults to `true`. Works in dev. Not a bug.

**G15. "No email adapter provided. Email will be written to console."** Expected until the email
adapter lands; see the later spec — per the owner's constraint it reads SMTP settings from an admin
global, not `.env`.

**G16. ESLint on generated files.** `payload-types.ts` carries its own `eslint-disable`;
`importMap.js` lints clean; generated migrations produce 4 `@typescript-eslint/no-unused-vars`
warnings (`payload`, `req` args). Either add `"migrations/**"` to `globalIgnores` in
`eslint.config.mjs` or accept warnings. No errors either way.

**G17. The CLI reads `.env` from cwd.** `generate:types`/`generate:importmap` do not connect to the
DB; `migrate*` do. `PAYLOAD_SECRET` is required by `buildConfig` for all of them. Next loads `.env`
too (`- Environments: .env`). Keep `.env` to `DATABASE_URL`, `PAYLOAD_SECRET` (and `NEXT_PUBLIC_
WHATSAPP_NUMBER` until it moves into a CMS global).

**G18. `'use client'` boundaries.** Nothing in the site changed. Payload's generated files use
`"use server"` in `(payload)/layout.tsx`; `importMap.js` must stay `.js` (template convention,
imported as `./admin/importMap.js`). `payload.config.ts` is server-only; never import it from a
client component (import `@payload-config` only in server components, route handlers, hooks).

**G19. `getPayload()` in a `(site)` server component is prerendered at build.** A page with no
dynamic API calls and a Local API read builds as `○ (Static)` and serves `x-nextjs-cache: HIT`.
This is the Phase 1 pattern for `generateStaticParams` + pages — it means **`next build` needs a
reachable, migrated Postgres**. Use `revalidatePath`/`revalidateTag` from Payload hooks to refresh.

**G20. Revalidation from hooks.** Importing `next/cache` inside `payload.config.ts` (via a
collection hook) does not break the CLI — `generate:types`, `migrate:create`, `migrate` all ran with
the hook present. Calling it works from REST and admin saves (verified `MISS` -> fresh render). From
a CLI/seed context (no request store) `revalidatePath` would throw — guard with
`if (!req.context?.disableRevalidate)` as the Payload website template does, and pass
`context: { disableRevalidate: true }` from seeds. Next 16 semantics: from Route Handlers (Payload
REST) `revalidatePath` marks the path and re-renders **on next visit**; from Server Functions
(Payload admin saves go through the `'use server'` function in `(payload)/layout.tsx`) it is
immediate. **`revalidateTag(tag)` with one argument is deprecated in 16 — use
`revalidateTag(tag, "max")`** (stale-while-revalidate) or `updateTag(tag)`.

**G21. Branded 404 needs extra work.** Unmatched URLs render Next's bare default 404 because the
global `app/not-found.tsx` requires `app/layout.tsx`, which no longer exists. Recipe (standard for
multi-root-layout apps, not exercised in the spike): `app/(site)/not-found.tsx` for `notFound()`
calls inside the site, plus `app/(site)/[...not-found]/page.tsx` that just calls `notFound()` so
unmatched URLs route into `(site)` and get its layout. `/admin/[[...segments]]` and `/api/[...slug]`
are more specific and are unaffected.

**G22. `next/image` and uploads.** Payload serves files at `/api/media/file/<filename>` — same
origin, relative — so `next/image` needs no `images.remotePatterns`. If `serverURL` is set in the
config, upload `url`s become absolute and the site host must be added to `remotePatterns`.

**G23. Not exercised, no reason to expect trouble:** `reactCompiler` (repo does not enable it;
Payload UI ships precompiled), `cacheComponents` (`withPayload` would set
`PAYLOAD_CACHE_COMPONENTS_ENABLED`), `typedRoutes`.

**G24. Hydration.** The site's `suppressHydrationWarning` + `data-intro` script are confined to the
`(site)` `<html>`; the admin's `<html data-theme …>` is a different document. No interaction.

**G25. Admin cold start in dev is ~7 s** on first `/admin` hit (compiling @payloadcms/ui), then
<100 ms. `next.config.ts` evaluation takes 1.7 s in build (loads `withPayload`). Normal.

## 6. `DATABASE_URL` connectivity (read-only probe, `pg` 8.20.0)

Queries run: `select version()`, `current_database()`, `current_user`, counts from
`information_schema`, `pg_extension`, `pg_roles`, `pg_stat_ssl`. Nothing written.

| Fact | Value |
|---|---|
| Server | PostgreSQL **16.15** on x86_64 Alpine (Docker; server addr 172.18.0.x), shared Nexeor host, port **5433** |
| Database | `maison_palettia_prod` — **empty**: 0 user tables, schemas `public` only, extensions `plpgsql` only |
| Role | `postgres` — **superuser, CREATEDB** |
| TLS | connection string has no `sslmode`; `pg_stat_ssl.ssl = false` — **plaintext over the public internet** |

Recommendations for Phase 1 (not blocking the spike):
1. Create a dedicated role (`maison_palettia_app`, `LOGIN`, owner of the DB or `CREATE` on schema
   `public`), not the superuser; Payload/drizzle only need DDL on its own schema + DML.
2. Either require TLS (`?sslmode=require` with a server cert, `pool.ssl`) or firewall port 5433 to the
   app server's IP / put both on the same Docker network. Today anyone on the path can read the
   credentials and the data.
3. Decide `idType` (`serial` default vs `uuid`) before the first migration.
4. `DATABASE_URL` and `PAYLOAD_SECRET` stay in `.env` on the host (`openssl rand -hex 32` for the
   secret). Everything else — Mamo Pay keys, SMTP, recipients, legal details — goes in admin globals
   per the owner's constraint (later spec).

Server (Docker, persistent disk) run order on every deploy:
`npm ci` -> `npx payload migrate` -> `next build` -> restart `node .next/standalone/server.js`
(cwd = repo root). Volumes: `media/`, `.env`. Backups: Postgres + `media/`. Single Node process
=> Next's default in-memory + filesystem ISR cache is correct ("single instance" in Next's
how-revalidation-works guide); if it is ever scaled to several processes/containers a shared
cache handler (`cacheHandlers`) is required or revalidation will only hit one instance.

### If it ever moves to Vercel
- No persistent disk: `media/` must go to `@payloadcms/storage-s3` (or Vercel Blob); set it from day
  one if that move is plausible.
- `output: "standalone"` is unnecessary (harmless).
- Migrations in the build command: `payload migrate && next build` (Payload's own Vercel template
  does exactly this), with `DATABASE_URL` reachable from Vercel's build network.
- ISR/revalidation cache is shared platform-wide — nothing to add.
- Serverless cold starts make the first `/admin` hit slow; Payload's `pool` must be small
  (`max: 1–3`) or go through a pooler.
- Any `payload` CLI job (`migrate`, seeds) runs in CI, never from the deployed function.
